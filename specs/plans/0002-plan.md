## #2 ve #3: doğrudan merge mi, feature/0002'ye alıp supersede mi?

| | A — Dependabot PR'larını doğrudan merge | B — feature/0002'ye cherry-pick, Dependabot PR'larını superseded kapat |
|---|---|---|
| Akış | `@dependabot rebase` → güncel main'de CI → onay → squash + `--match-head-commit`; ikinci PR ilk merge'den sonra yeniden rebase + CI | Dependabot commit'leri `git cherry-pick -x` ile feature/0002'ye alınır; 0002 PR'ının head'inde CI; #2/#3 "superseded by #N" yorumuyla kapatılır |
| main'e merge sayısı | 3 (iki Dependabot + 0002) | 1 (0002) |
| Work item içinde sıra | Dependabot merge'leri VERIFY'dan önce main'e girmek zorunda (CB-7 ship öncesi); feature/0002 sonra rebase edilir. SHIP gate'i iş ortasında iki kez açılır | Tek BUILD → REVIEW → VERIFY → SHIP döngüsü; CB-7 VERIFY'da doğal olarak doğrulanır |
| CI kanıtı | Her PR kendi head'inde, ayrı ayrı | Tek head'de, bütün değişiklikle birlikte (gerçekte çalışacak kombinasyon) |
| Provenance | Dependabot PR'ı ve gövdesi (release notes, compat) main geçmişinde | Cherry-pick yazarı (`dependabot[bot]`) ve `-x` satırını korur; #2/#3 0002 PR'ına bağlanır |
| Geri alma | Her action ayrı commit → tek tek `git revert` | Squash sonrası tek commit → bir action'ı geri almak için küçük bir elle düzeltme |
| Dependabot durumu | Dependabot kendi PR'ını merge edilmiş görür | Elle kapatılan PR için Dependabot o sürümü bir daha önermez; main zaten v7/v6'da olacağı için etkisi yok |

**Öneri: B.** Gerekçe: spec 0002 bu yükseltmeleri tek work item'ın parçası yaptı ve ship öncesinde
VERIFY'da doğrulanmalarını istiyor. A bunu, VERIFY'dan önce main'e iki ayrı merge yaparak ve
feature/0002'yi araya rebase ederek sağlar; SHIP gate'i iş ortasında parçalanır. B'de tek
current-head CI kanıtı, tek review, tek VERIFY ve tek SHIP gate'i var; ayrıca CI gerçekten
birlikte çalışacak kombinasyonu (v7 + v6) test eder. Kaybedilen tek şey action başına ayrı revert
commit'i; CI dosyasında iki satırlık bir geri alma için bu kabul edilebilir. Cherry-pick, Dependabot
yazarlığını ve kaynak commit'i koruduğu için izlenebilirlik kaybolmaz.

- **R-1 — Dependabot'un elle kapatılan PR davranışı.** O sürümü bir daha önermez, branch'i silebilir
  ya da bırakabilir. *Öneri:* kapattıktan sonra `git ls-remote` ile kontrol; kalan branch CB-2
  politikasıyla silinir. main v7/v6'ya geçeceği için "bir daha önermez" davranışı zararsız.
- **R-2 — Bulgu 3 (default branch silinmesi) kanıtı.** Yazma işlemiyle denemek yok. *Öneri:* BUILD'de
  GitHub dokümanından atıf; doğrulanamazsa ADR 0007 temkinli ifade kullanır ve bunu açıkça yazar.
- **R-3 — PR #5 retrospective review bulgu çıkarırsa.** *Öneri:* triage'a girer; Git/süreç
  kapsamındaysa 0002'de düzeltilir, değilse ayrı work item. (Diff tek satır `.gitignore`; bulgu
  beklenmiyor.)
- **R-4 — #2/#3 kapanışı merge sonrasına kaldı (insan kararı).** Sonuç: CB-7'nin "#2/#3 açık
  kalmaz" kısmı ve CB-2'nin Dependabot branch'leri kısmı VERIFY'da değil, SHIP'te merge sonrası
  kanıtlanır (ship-time evidence, 0002 PR'ına yorum). CB-7'nin geri kalanı (v7/v6, release notes,
  onaylar, current-head CI) VERIFY'da doğrulanır. Spec'in "ship edildiğinde" final state tanımı
  SHIP adımının bu merge sonrası kısmıyla karşılanır.
- **R-5 — Merge sonrası durum VERIFY'dan sonra oluşur** (feature/0002 branch'inin otomatik silinmesi).
  *Öneri:* SHIP'te `git ls-remote` çıktısı 0002 PR'ına yorum olarak eklenir; VERIFY tablosu bunu
  "ship-time evidence" olarak işaretler.
- **R-6 — Yeni gate'i kendi PR'ımızda uygulamak.** 0002 PR'ı yeni template maddesini ve kuralı ilk
  kullanan PR olacak. *Öneri:* bilinçli; merge öncesi head SHA kanıtı PR'a yazılır.
